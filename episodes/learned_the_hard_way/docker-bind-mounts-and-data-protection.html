01 The incident

After a reboot on NXCore (~12:16), the live tree at /srv/ACOS/workspaces on the ACOS ext4 volume (/dev/sdc1) came back empty — wiped or recreated without its prior contents. Compose stacks that depended on those host paths were brought up (or remade mounts) against a hollow tree.

Docker’s default behavior filled the gap: for each missing bind source, it created a directory on the host. Where a mount expected a file (config, binary, entrypoint script), that directory stub broke the container — classic Exit 127 (“command not found”) when a path that should be an executable file is suddenly a folder.

Authority boundary. Staging and preview are safe. Live cutover (replace hollow with restored trees) is operator-approved only, one app at a time. No undelete, prune, or stack start on empty workspace roots without inspection.

Timeline in one breath

Reboot → workspaces SoT empty → Docker remade hollow host dirs for missing binds → file binds became directories → containers fail (often Exit 127) → leave hollow alone → stage recovery under _recovery/ → validate in _restored_preview/ → cutover only with approval.

Recovery pattern used (stage → preview → cutover)
  1. Do not overwrite live hollow stubs.
  2. Stage extracts (tmp, image cp, container export, named volumes) under a dated recovery path.
  3. Restore one app to a preview path only; validate (DB, inventory, secrets hygiene).
  4. Cutover: rename hollow → .hollow-bak, then promote preview — with explicit approval.

02 Why Docker does this

A bind mount maps a host path into a container. If the host path does not exist when the container starts, Docker Engine creates it as a directory. That is convenient for directory mounts. It is catastrophic when Compose expects a file.

File bind + missing source = hollow directory. The next start “succeeds” at mount time and fails at runtime. You have silently replaced a config or binary with an empty folder on the host.

Why Exit 127 shows up

Exit 127 usually means the shell could not find the command. If your entrypoint is bind-mounted from the host and that path is now a directory, the kernel cannot execute it. Same story for scripts, .env files wrongly mounted as dirs, or cert files that became folders.

Named volumes vs binds

Named volumes live under Docker’s volume store. They survive workspace-tree wipes on a separate disk as long as the Docker data root is intact. Directory binds to large trees are clearer than file binds: type mismatches are rarer, and you can check size/inventory before start.

Prefer named volumes or directory binds for durable state. Reserve file binds for cases you can preflight (path exists, is a file, minimum size).

04 Protection playbook

Actionable habits. Do these before stacks touch a shared workspace root.

  1. Preflight before compose up

    For every bind: path exists; files are files; dirs are dirs; critical files have a minimum size. Refuse start if any check fails.

  2. Prefer named volumes / directory binds

    Avoid file binds when possible. Directory mounts and named volumes fail more loudly and recover more cleanly than “file became a folder.”

  3. Back up critical bind roots

    Snapshot or sync workspace trees that are SoT. Know which data lives on ACOS vs NXDrive. Do not start stacks on an empty workspace after reboot.

  4. Post-incident: inspect mounts before start

    Compare hollow stubs to expected inventory. Treat unexpected empty dirs as a stop signal — not as “Docker will fix it.” Disable or refuse auto-mkdir surprises in your ops runbook.

  5. Recovery: stage → preview → approved cutover

    Stage elsewhere. Validate one app under a preview path. Cutover only with operator approval. Keep hollow backups until the app is verified live.

Rule of thumb. If the workspace root looks newly empty after a reboot, stop. Inventory first. Compose second.
